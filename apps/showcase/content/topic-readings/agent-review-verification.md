# 如何驗收 Agent 的工作，知道測試究竟證明什麼？

[回專題入口](../../../../docs/insights/topics/index.md) · 首次整合 · 11/1–11/14 選定的 10 個來源

**先定義交付條件，再把文件、流程、模型與實際操作分開驗證。** 多支影片都談「檢查 AI」，但檢查的對象不同；一次通過不能直接推成整個系統可靠。

適合正在交辦程式修改、自動接單或多步驟 Agent 的情境。本篇依已收錄摘要整合，沒有重新安裝工具、執行原影片實驗，或獨立查核產品與跑分。

## 把檢查放回它能回答的問題

|要回答的問題|來源提供的方法或案例|能證明的範圍與限制|
|---|---|---|
|需求有沒有漏掉失敗情境？|讓未參與原討論的新對話，只看設計文件來挑錯。|有助暴露文件缺口，不證明程式已正確實作。[V3][V4]|
|補充訊息、工具回報是否歸到正確任務？|faux provider 用預設回應跑實際任務與狀態處理。|可檢查流程；不測真實模型推理、服務、網路或效能。[V2]|
|程式邏輯與安全檢查有沒有漏看？|控制 Code Review 的範圍、規則與上下文；另有安全掃描案例。|評論少雜訊不等於不漏報；掃描報告仍需核對，不能保證沒有漏洞。[V5][V6]|
|真實任務能否做出可用結果？|依具體情境設計模型評估與原型；交付附修改範圍及證據。|特定案例不代表所有任務有效，也不表示單一指標能涵蓋整份交付。[V8][V10]|
|實際使用時是否符合完成條件？|pstack 案例分別檢查程式測試，再由創作者操作表單、預覽、複製與窄螢幕。|兩類檢查互補；這次網頁操作由人完成，不能算成 Agent 已自動驗收。[V1]|

這張表是整理者對來源的分層，不是每部影片原本就採用同一套分類，也不是一套已實測的標準作業流程。

## 相似內容放一起，但保留新增細節

兩支 Elephant-Goldfish 的共同方法只需說明一次：先在有完整脈絡的對話整理設計，再讓沒有參與討論的新對話只看文件挑錯。[V3][V4]

後一支補足怎麼問：文件是否交代付款失敗、重複執行會怎樣，以及還有哪些疑點使實作者無法開工。值得保留的是這些檢查條件；使用人數、星數與影片宣稱的改善比例，不作效果結論。[V3]

SuperAgent 的三份來源也可以合讀：架構說明任務授權、Router／Worker、狀態與訊息送出的安排；GitHub 與飛書影片補充從不同入口交辦及以 PR 檢查交付的案例。原型摘要明示隔離與真實交付尚有驗證缺口，操作展示不能抹去這個限制。[V7][V8][V9]

## 這次多理解了什麼

這是首版，沒有前一版可比較。本次選材中，11/1 週的內容已談接單、審查與人工看 PR；11/8 週補上 faux provider 的明確測試邊界，以及 pstack 把完成條件落到具體畫面行為的案例。[V2][V7][V8][V1]

它們讓「有測試」變成更精確的問題：**這個測試檢查了哪一層，還有哪些層沒有檢查？** 模擬回應能幫忙重現歸屬錯誤，卻不能用來宣稱模型會選對工具；自動化測試通過，也不能把創作者親自完成的網頁操作算成 Agent 自行完成。[V2][V1]

## 不能合併成一個好消息的地方

OpenCodeReview 摘要同時提到精確率與召回率的取捨。即使較少誤報，也可能漏掉問題，不能簡化成「審查更準所以可以放心」。影片中的測試數字未由本次另外查證。[V5]

SecVibe 的摘要則描述掃描出支付與登入等安全風險；這能補足關注面向，但未提供本次可核對的完整重現、修復與回歸證據。不能因摘要說重新掃描，就判定風險已經排除。[V6]

目前沒有足夠資料建立同一測試條件下的可靠矛盾或工具勝負；以上是不同驗證範圍與證據限制，不能硬寫成產品彼此打臉。

## 可以怎麼運用

以下是依來源提出、尚未在本專案做成效實驗的試用方式：選一個小任務，先寫清楚成功、失敗和重複操作的預期；用固定回應重現流程，再另驗證真實模型和服務。交付時，對照程式檢查與實際使用證據，清楚列出沒測的部分。

以表單為例，要求「能送出」仍太模糊；可具體問漏填如何處理、預覽與複製是否一致、修改輸入後舊結果是否失效。這些條件來自 pstack 摘要的案例，仍需依自己的任務調整。[V1]
